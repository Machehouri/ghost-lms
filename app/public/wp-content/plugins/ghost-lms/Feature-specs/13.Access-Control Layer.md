# 13 — Access-Control Layer

Read `context/AGENTS.md` and all context files before starting.
Depends on: 04-roles-capabilities, 11-enrollment-on-purchase.

## Goal
Build the single, central "can this user see this course's content" check that
every future content-gating decision — lesson player, quiz, forum, certificate
download — calls into. This is the concrete implementation of the architecture
invariant: every route/template that gates content goes through one access
layer, never a re-implemented check.

## Design decisions
- One class, `src/Access/CourseAccess.php`. Its core method,
  `can_view_course_content(int $user_id, int $course_id): bool`, is true if any
  of: the user has an active enrollment (via `EnrollmentRepository`), the user
  is the course's owning instructor, or the user is an administrator.
- This unit builds the **base** check only — enrollment, ownership, admin. It
  does **not** implement drip-content or prerequisite rules; those wrap this
  base check in Phase 5 ("enrolled AND unlocked") rather than being built into
  it now. Keeping this method narrow is deliberate — it's the one thing every
  later gate depends on, so it needs to stay simple and stable.
- A REST-oriented helper, `CourseAccess::rest_permission_callback( WP_REST_Request $request ): bool|WP_Error`, so REST controllers can use a one-line permission callback (`[CourseAccess::class, 'rest_permission_callback']`) instead of re-deriving the course ID and re-checking access inline each time.
- A template-oriented helper, `CourseAccess::current_user_can_view( int $course_id ): bool`, wrapping the core method with `get_current_user_id()` for use directly in PHP templates/blocks.
- Ship one genuinely useful, permanent REST route alongside this —
  `GET /ghost-lms/v1/courses/{id}/access-check` — both as a way to verify the
  logic end-to-end now, and because the frontend will want a lightweight "am I
  enrolled" check later (e.g. to decide whether to show a "Continue" vs.
  "Enroll" button) without fetching the whole course object.

## Implementation
1. `src/Access/CourseAccess.php` — implements the three checks above, depending on `EnrollmentRepository` (spec 11) and `Capabilities::current_user_can_manage_course()` (spec 04).
2. `src/Rest/AccessCheckController.php` — registers the `access-check` route, calls `CourseAccess::can_view_course_content()`, returns `{ "can_view": true|false }`.
3. PHPUnit tests (per `03-code-standards.md`'s testing guidance, which calls out access-control logic specifically) covering all six scenarios below.

## Verification checklist
- [ ] `can_view_course_content()` returns `true` for: an actively enrolled student, the owning instructor, an administrator.
- [ ] `can_view_course_content()` returns `false` for: a logged-in but non-enrolled user, a different (non-owning) instructor, a logged-out visitor.
- [ ] All six cases above are covered by PHPUnit tests, not just manual verification.
- [ ] The `access-check` REST route returns a result consistent with calling the method directly, for an enrolled and a non-enrolled user.
- [ ] This unit is purely additive — confirm no existing route or template needed to change, since Phase 4 will be the first real consumer of this layer.
